Machines That Agree With Each Other

I keep a CLAUDE.md in my Nix configuration repository, for now.

It explains the layout of the project, the commands that rebuild each machine, and the decisions that are easy to get wrong. It tells the agent not to invent custom NixOS options for values read in one place. It discourages conditional wrappers where a direct assignment would do. It explains why my work Mac is configured differently from my personal Mac.

The file is useful, and it's the least durable part of the setup. I'll replace Claude Code with another agent at some point. The next tool may read a different instruction file, interpret the same sentences differently, or ignore them in new ways. I'll also forget some of my own rules, or convince myself a small change doesn't need the full process.

Any constraint that protects my machines can't depend on the current editor, human or otherwise, reading a document and complying. It has to live in the repository.

The repository configures four machines: two NixOS hosts, a personal Mac managed with nix-darwin and Home Manager, and a work Mac where Home Manager owns the dotfiles and Homebrew owns the software. Changes arrive from me, from a coding agent, and from a dependency-update workflow. All three meet the same configuration model and the same checks.

That's what I mean by machines agreeing with each other: the four hosts, plus Nix, the formatter, the linters, the secret scanner, CI, and the branch rules, all holding a diff to the same standard no matter who produced it.

None of them proves a change is correct. Each answers a smaller question. Nix asks whether the configuration evaluates. The formatter asks whether the source has the expected shape. The linters look for specific mistakes. The secret scanner looks for credentials and private names. CI repeats the checks in a clean environment, and the repository rules decide whether a failed check blocks the merge.

None of these systems trusts the author much, which is useful now that the author is hard to identify.

Writing my preferences down saves time. The first diff is better and I stop repeating the same review comments.

The instruction file is still prose, though. The agent can misunderstand it. A long session can push the relevant sentence out of context. Two rules can conflict. The agent can follow the words and miss the reason I wrote them. A human can skip the file without noticing it exists.

Some preferences can't be tested at all. There's no reliable check for "an abstraction for a hypothetical future user," and I'm not going to build a classifier for taste. That kind of rule belongs in documentation and review.

The distinction I care about is between preferences and invariants, and it has nothing to do with whether a human or a machine wrote the code. A preference describes how I'd like a change made. An invariant describes what must still be true after the change. Instruction files communicate preferences. Mechanisms enforce invariants. A rule the editor can ignore is a suggestion with better formatting.

It doesn't solve the other wiring problems. A newly loaded feature still has to be enabled in the right host configuration, and a stray Nix file under that directory gets loaded whether I meant it or not. Mechanisms don't remove trade-offs. They let me pick which mistakes are hard to make and which are obvious once made.

Those checks run nixfmt, deadnix, statix, actionlint, and Gitleaks. Together with the evaluation step they catch broken option references, malformed modules, formatting drift, invalid workflows, dead Nix code, and recognized secrets.

The same hook set also validates commit messages with commitizen, but only on my machines at commit time. The CI derivation runs the pre-commit stage and skips commit-msg hooks, so a bad commit message reaches main if I bypass the hook locally.

Evaluating is weaker than building. Asking for a derivation path shows Nix can evaluate the expression far enough to produce a build plan. It doesn't build the system closure, boot the NixOS machines, activate the Mac configuration, or prove the result does what I intended.

A valid Nix configuration can disable SSH. It can drop a package I still need, expose a service, replace a key, or make a bad architectural decision, and evaluation passes. Nix verifies the structure of the configuration. It can't infer my intent.

That gap matters more here than in a repository nobody deploys automatically. The desktop and the personal Mac pull main and switch to it unattended once a day, and the work Mac reapplies its dotfiles at login. A change that evaluates cleanly and behaves badly reaches three machines by the next morning.

I auto-merge narrow dependency updates once the checks pass. I don't treat the same green check as permission to merge arbitrary changes to storage, networking, accounts, or permissions. A daily workflow bumps one flake input at a time, opens a pull request for each, and enables auto-merge on it, and that's the extent of the automation. Review isn't obsolete. The mechanism is useful because its claim is narrow.

A mechanism has a scope

My personal Mac configuration includes this nix-darwin setting:

On activation, Homebrew removes formulas and casks the configuration doesn't declare. Something I installed ad hoc and forgot about doesn't become permanent. The next activation reconciles the machine with the declared state.

My work Mac doesn't do that. Its Brewfile workflow is additive: Homebrew installs what I declare, and cleanup is a separate command I run after reading its output. I don't want a personal configuration repository deleting software my employer manages. The README documents the difference.

The rule is to make ownership explicit and reconcile only what this system owns. A guardrail with no scope is an accident waiting to happen.

The personal machines get their identity from the Nix configuration. The work Mac reads an untracked, machine-local work profile. If the expected identity is missing, Git refuses to invent one from the local username and hostname.

That turns a quiet mistake into an immediate failure. Git doesn't care whether the identity vanished because an agent edited the wrong module, I misconfigured a new machine, or someone cloned the repository and kept my values. It knows a required input is absent.

Secret scanning has a different boundary. The committed Gitleaks rules run in the pre-commit checks and in CI. That limitation is easy to miss when I describe the system by feature: "I have secret scanning." The better description says where the scan runs, with which rules, and on which paths into the repository. A mechanism is only real where it executes.

A check can be a gate or an alarm

CI runs on pull requests and on pushes to main, unless the change only touches Markdown. Branch protection requires the check on the pull-request path, so a dependency update can't auto-merge until it passes.

Direct pushes from me aren't gated. The protection doesn't apply to administrators, and I'm the administrator, so a broken direct push lands on main and CI reports the failure afterward.

On one path the check is a gate. On the other it's an alarm. The YAML is identical. The difference is where the check sits relative to the action it's meant to prevent.

The same applies outside GitHub. A test that runs after deployment tells you production is broken and doesn't prevent it. A secret scanner that runs after the commit helps you find the credential and doesn't save you from rotating it. A configuration check that runs after a machine switches makes the failure visible and leaves the machine broken. Whether a check exists matters less than whether the path you care about can route around it.

I don't describe my setup as making unreviewed changes "safe." It reduces risk for specific changes on specific paths. That's a smaller claim, and one I can defend.

It also hands me the next improvement: apply the protection to administrators too, which is one checkbox on GitHub and forces my own changes through the pull-request path, or accept that direct-push CI is an alarm and say so.

The editor is temporary

I still keep the instruction file. It documents the architecture and the choices I can't reduce to a test, for future me, for anyone borrowing from the repository, and for whichever agent I use next. It improves the starting point. I've stopped treating it as the safety boundary.

An agent is an editor. It proposes a diff. A human contributor is also an editor, and so am I. The repository shouldn't grant my changes extra credibility because I typed them. I make syntax errors. I forget imports. I commit with the wrong identity. I install something temporarily and leave it behind. I misread the scope of checks I wrote myself. Enforcement should be indifferent to authorship.

Some preferences should stay preferences: whether an abstraction is worth its cost, whether a dependency is justified, whether a valid change makes the project easier to understand. Encoding all of that in CI would produce a rigid, unpleasant codebase. But once I can state a rule precisely and check it repeatedly, leaving it in prose means choosing my memory as the enforcement mechanism.

I'll replace my current coding agent. Other people will change this code. Future versions of me will change it tired, distracted, or overconfident. The tools will change. The safety model shouldn't have to. The goal is machines that agree with each other, whoever writes the next change.
